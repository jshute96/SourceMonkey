Userscript examples for @run-at

Header

  • @run-at document-start — runs before the DOM has parsed. document.readyState is loading and document.body may be null.
  • @run-at document-end — runs after DOMContentLoaded, before subresources finish. readyState is interactive.
  • @run-at document-idle — default. Runs after load. readyState is complete.

Details

  • Three userscripts match this page, one per @run-at value. Each appends one row to the log with the readyState it observed.
  • You should see one row per variant, each with a t=...ms timestamp (milliseconds since navigation start). The page’s own lifecycle events (inline-script, DOMContentLoaded, load, …) are also rendered into the same log so the timings line up visually.
  • This page deliberately pulls in a slow sync script (/__slow/blocker.js?ms=400) in <head>. It blocks the parser at readyState=loading for ~400ms while leaving the main thread free for userscript injection — so document-start has a chance to run during the loading phase before DCL.
  • The delay needs a server that implements /__slow/: use node scripts/serve-examples.mjs from the repo root. Over file://, or via a generic static server like npx http-server, the /__slow/ fetch 404s instantly and all three variants converge after load like the no-delay case; a runtime banner below points this out.
  • In practice the readyState observed by each variant depends on the manager. Under Tampermonkey we typically see the clean three-state split (start=loading, end=interactive, idle=complete). Under Chrome’s chrome.userScripts, document-end and document-idle often batch together in a single post-load injection burst and both observe complete.
  • The page also logs lifecycle markers into window.__SM_PAGE_TIMING__ if you prefer to inspect them from DevTools.
