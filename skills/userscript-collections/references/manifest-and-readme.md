# The manifest, README tables and site icons

## `script_manifest.json`

The list of scripts SourceMonkey (the userscript manager) loads from
the collection, and the collection's source of truth for which scripts
exist. Add and remove script entries with `sm-dev manifest` (see
SKILL.md); edit the other fields by hand, except for the generated ones
below. It's an object with two lists:

```json
{
  "scripts": [ ... ],
  "libraries": [ ... ]
}
```

SourceMonkey reads each script entry's `path` and ignores every other
field and top-level key, so the tools here (and other skills, like
`publish-on-GreasyFork`) keep their own fields beside it.

### `scripts`

One entry per userscript, in site order (by path). An entry is a plain
path string, or an object with:

* `path`: the relative path from the collection root. Required.
* `category`: which README table the script belongs in. Omit it for the
  default table (the same as `"default"`).
* `site_icons`: the icons shown before the script's name: its own
  `@icon`, or else the favicon of each site it runs on, as
  SourceMonkey's collections page shows them. Paths from the root,
  mostly into `site-icons/`. Generated by `update_site_icons.py`.
* `site_icons_pinned`: `true` keeps `site_icons` and its files as they
  are, for an icon fixed by hand. Use it for a site that only shows its
  real favicon when logged in (the temp browser never is).
* `greasyfork`: the script's Greasy Fork id and URL, for a collection
  that publishes there. Written by the `publish-on-GreasyFork` skill;
  `update_readme.py` links it in the `GF` column.

### `libraries`

One entry per shared `@require` helper (a plain `.js` file with no
metadata block, often in `lib/`). They aren't userscripts and
SourceMonkey doesn't load them directly, so they're listed only to
track what exists, give them a README table, and record where each is
published:

```json
{
  "path": "lib/shared-helper.js",
  "github_url": "https://raw.githubusercontent.com/me/userscripts/main/lib/shared-helper.js"
}
```

* `path`: required.
* `github_url`: the raw URL scripts `@require` the library by, written
  by hand. `publish-on-GreasyFork` uses it to map those `@require`s to
  Greasy Fork, and adds a `greasyfork` field of its own.

Each library's first line is a one-sentence `//` comment saying what it
is; the README table shows it as the description.

## `README.md` tables

Generated by `update_readme.py`. Each table sits under a placeholder
comment. A script table's placeholder is:

```markdown
<!-- update_readme.py [category=<name>,...] [manifest=<path or URL>] -->
```

* `category=` names the categories the table shows, merged into one
  table. Without it, the table shows all the manifest's scripts. Each
  category named has to be in the manifest.
* `manifest=` lists another collection's scripts instead, from its
  manifest's path or URL (see `--help`). It's rarely needed.

The manifest's `libraries` (shared helper `.js` files that scripts
`@require`) get a table of their own:

```markdown
<!-- update_readme.py libraries -->
```

Everything from the line after a placeholder up to the next blank line
is replaced by the generated table:

```markdown
<!-- update_readme.py category=tools -->
| Site | Script | Doc | GF | Description |
| :---: | --- | --- | --- | --- |
| <img src="site-icons/example.com.png" ...> | [Example: Fix the thing](sites/example.com/fix.user.js) | [doc](sites/example.com/fix.md) | [GF](https://greasyfork.org/scripts/...) | What it does. |
```

Run it after adding or removing a script or library, or when a
script's `@name`, `@description` or icons change. `--check` reports
what's stale without writing. Each run ends by listing what no table
shows, by manifest (`Not in any table: ...`): check it after adding a
script. `update_readme.py --help` has the rest: columns, and other
collections' manifests.

### Categories

Scripts omit `category` by default, and then go in the `default`
category. To put a script in another category, set `category`, and
make sure a placeholder shows it, either by naming it or with no
`category=`. A category can be in more than one table.

## `site_icons` and `site-icons/`

Generated by `update_site_icons.py`, which starts an `sm-dev` run
(SourceMonkey's development tool) in a temp browser (a fresh,
logged-out profile) with the scripts and saves each one's icons (`sm-dev
script N save --include icon,site-icons`). Run it after adding a
script, or changing its `@icon` or `@match` lines, then run
`update_readme.py`.

* Name scripts (`update_site_icons.py sites/x/y.user.js`) to update
  just those; the rest keep their icons.
* Scripts `sm-dev validate` finds invalid are skipped and keep their
  icons, since a run can't load them.
* Scripts with the same remote `@icon` share one file, named for its
  URL.
* Site icons come from the live sites, so a full run can also pick up a
  site's new favicon.
* Scripts on the same site share one file. Files no script uses any
  more are deleted.
* It needs `pnpm sm-dev` working in the checkout it's run from (the
  `sourcemonkey` dev dependency), and Pillow (the Python imaging
  library, `python3-pil`) to scale icons down.
* `--run <id>` uses an `sm-dev` run that already has the scripts
  loaded, instead of starting one.
